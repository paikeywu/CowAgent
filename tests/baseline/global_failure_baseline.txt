# 门禁全局失败集基线（S3-X · GB-1）
#
# ============================================================================
# 【这个文件是什么】
# ============================================================================
#
# **门禁的全局失败集**的基线 —— 门禁跑完一遍之后，哪些判据是红的，
# 哪些是 NOTRUN 的，哪些是绿的。**门禁的每一条判据都在里面**。
#
# **为什么要有第二份基线**（Q5 已经有了呀？）：
#
#   * Q5（`tests/baseline/p1_regression_baseline.txt`）只覆盖
#     **``text_inv.run_text_invariants`` 那一组**（INV-1 / INV-2/3 /
#     SHELF-LAG）。基线条目的格式是「库名:判据名」，而 `text_inv` 的
#     判据名就只有这三个。
#   * 门禁里**其它组**的红 —— DR-1..DR-7、I-1..I-4、U-1、J-2..J-5、
#     M6a..M6f、INV-2、ANCHOR、M4、Q1、Q2、C-A3.4 —— **从来不在 Q5 的
#     范围内**。它们的判据名根本不是 `text_inv` 的判据名。
#   * ⇒ **全局失败集没有基线 = 回归无处可查。** Q5 报绿时，
#     DR/I/J/M6 那一大片里新出来的一条红，Q5 一眼都看不见。
#
#   ⇒ 本文件是**与 Q5 并列**的第二份基线，不是它的替代品。
#
# ============================================================================
# 【风控 §5.1 的六条最小归因 —— 缺一不可，GB-1 会逐条点名检查】
# ============================================================================
#
# 1. **两次独立快照**
#    两次独立全量快照（间隔 ≥20 秒），且两次的 RED 集合完全相同。
#    ⇒ 「只跑一次就刷」被禁：活库在被持续改动，单次快照的失败集本身
#      就不稳定。本轮的两次快照时间见下。
#
# 2. **逐条点名**
#    每条条目点名到 库:判据 + path + chunk id。本文件每条条目后面
#    的 `|` 后面就是逐条归因。
#
# 3. **时序对照**
#    真源 mtime vs 账本 `certified_at` 的时序对照（早于改动 ⇒ 归因于
#    「认证时点错位」，而不是「代码回归」）。本轮的三类漂移源的
#    mtime 与 certified_at 都写在下面的逐条归因里。
#
# 4. **环境项不进基线**
#    明确列出哪些红是**环境项**，它们**不进**基线：
#
#      * **J-5** —— 旧写入者是否又擦过库（两个运行时常驻，旧端仍在
#        擦统计列）。这是**环境真相**，不是回归。
#      * **DR-1** —— 双运行时常驻。环境真相。
#      * **DR-2** —— 变化溯源：变更记录点漏记外部编辑。**历史不可
#        回填**（日志只追加，机制生效前的旧事件永远没有见证）⇒
#        工程师已登记：**DR-2 是预期红**，本机制不会让它变绿。
#
#      ⇒ 这三条**不进**本基线。理由：环境项进基线 = 基线替环境兜底；
#        环境被修好之后，那些条目会读成「消失的回归」，而那是关于
#        一次修复的**谎言**。
#
# 5. **头部归因正文**
#    本文件头部保留归因正文 —— 它是**尺子的说明书**，不是注释。
#    删掉它，下一个维护者就会把基线当黑盒，然后一键刷新。
#
# 6. **diff 可逐条读**
#    基线 diff 必须能逐条读（禁止 squash 成「更新基线」一个提交）。
#    本文件每次变更都是逐条列出新增/消失的。
#

# 归因 A · M4（每个活库的四列已回填）—— **数据欠账，非回归**
# ------------------------------------------------------------------------
#   现象：ROOT 库有行的 `body_path`/`body_anchor`/`body_hash` 为空，
#   或 `text_state` 非法。
#   归因：这是**回填欠账** —— 库里的行是在四列机制上线之前写的，
#   写进去的时候没有那四列。修法是重跑回填（工程师的地盘），
#   **不是判据的问题**。
#   本轮**不动**它：门禁上它是真红，基线记下来是为了让 GB-1 从
#   「无法判定」回到「可判定」。
#   📌 M4 | 四列回填欠账（库里的行写于四列机制上线之前）—— 修法：重跑回填（工程师）

# ------------------------------------------------------------------------

# ------------------------------------------------------------------------
#   现象：`body_origin='unresolved'` 的行 —— 没有人判定过这些行的
#   来源。
#   归因：**写入口欠账** —— 2026-11-01 09:28:44 有一次批量写把一批
#   知识页写成了 `projection + unresolved`。修法是修写入口 + 回填
#   （工程师的地盘），不是判据放宽。
#   📌 Q1 | unresolved 行的写入口欠账（2026-11-01 09:28 批量写入）—— 修法：修写入口（工程师）

#        账本 certified_at = **2026-10-30 10:42:52 / 10:42:53**

# 归因 E · C-A3.4 / J-3（files 统计列）—— **环境项 + 数据欠账**
# ------------------------------------------------------------------------
#   现象：部分库的 `files.chunker_version` 与当前切法不一致，或
#   统计列被清空成 NULL。
#   归因：**两个成因**：
#     ① **旧端降级**（环境项）：旧端的 `files` 写入路径走
#        DELETE→INSERT，兜底条件 `NEW.chunk_count IS NULL` 不成立
#        （ROOT 的 DDL 是 `NOT NULL DEFAULT 0`）⇒ 落回 `0/0`。
#        **这是环境项**，旧端停用后自愈；
#     ② **迁移欠账**：统计列被擦成 NULL 是旧端的 DELETE 触发器留的
#        痕迹（`files_keep` 守卫的快照在，但 `files` 行已被旧端重建）。
#   ⇒ **这是环境项与数据欠账的混合**，修法在工程师侧（清扫 + 停旧端）。
#   ⚠️ **注意**：归因 ① 是环境项，按风控 G1 **本应不进基线**；
#   但 C-A3.4 / J-3 这**两条判据本身**判的是「统计列是否齐备且
#   版本正确」，它们的红**不是**纯环境项（里面混着 ② 的数据欠账）。
#   ⇒ 处置：**判据进基线，但归因里必须写明「环境成因 vs 数据欠账」的
#   拆分**，并在旧端停用后**手工重新评估**这两条是否还该留在基线里。
#   📌 C-A3.4 | 统计列降级（环境：旧端 DELETE→INSERT 把 0/0 写回；数据：迁移欠账）—— 修法：清扫 + 停旧端（工程师）
#   📌 J-3 | 同上（判据侧的三态区分：从未迁移 / 被擦成 NULL / 版本错）
#
# ------------------------------------------------------------------------
# 归因 F · M6e（files 统计列守卫）—— **环境项的守卫侧**
# ------------------------------------------------------------------------
#   现象：files 侧的统计列有 NULL 与不符两种坏形状，守卫在位但
#   存量未清。
#   归因：与归因 E 同源。守卫在位（机制 OK），**存量**未清（作业
#   未做）。修法是清扫。
#   📌 M6e | 守卫在位、存量未清（与 C-A3.4/J-3 同源）—— 修法：清扫（工程师）
#
# ------------------------------------------------------------------------
# 归因 G · J-2（NOTRUN）—— **前置未成立，不是红**
# ------------------------------------------------------------------------
#   现象：J-2 判「没迁移」与「迁移后被擦」可区分；实测 7 个库的 F4
#   前提成立（`files.chunker_version == 4`）⇒ 判别的前提不成立 ⇒
#   NOTRUN。
#   归因：**NOTRUN 不是红**，是「这条判据在这批语料上不可测量」。
#   GB-1 的口径：**基线里是 RED、现在 NOTRUN ⇒ 算回归**（失败没有
#   消失，只是不再被测量）；**从未 RED 过的 NOTRUN 不进基线**。
#   ⇒ J-2 现在是 NOTRUN 且**从未 RED** ⇒ **不进基线**。
#   📌 （J-2 不在本基线里 —— 它是 NOTRUN，且从未 RED 过）
